The data model below supports the different workflows of Landlord Rep and Tenant Rep brokers — they share the same foundation but diverge in how the deal pipeline is structured, just like their business.
Key design decisions in this data model
Parent–child deals: Each broker-client relationship starts with a parent "agreement" deal. Individual property transactions sit underneath it as children — so everything stays connected and reportable together.
Contact spanning companies: A contact who works across multiple companies (e.g. a tenant with multiple subsidiaries) is linked to all of them — no duplicate records needed.
Ownership transfers: Properties are linked to their owner in a way that allows ownership to change hands without losing any historical data about the building.
Space counts roll up automatically: The number of vacant, live, and expiring spaces on any property is calculated automatically — no manual tallying required.
Contract hierarchy: When a deal closes, the executed lease is automatically filed under the original rep agreement — giving a complete history of every deal ever done under one client relationship.

Tenant Rep Pipeline — Option A vs. Option B
Option A  ·  Track candidates separately, create a deal only when it's real     Option B  ·  Create a deal record for every space from day one
What changes Option A — Separate tracking for candidates Option B — One deal record per space, from the start
How it works The broker maintains a shortlist of candidate spaces. Only when a space gets an LOI (letter of intent) does it become a formal deal record. Everything before that lives in a separate "evaluation" list. The moment a broker adds a space to their book, it becomes a deal record — just like the Landlord Rep workflow. Most of these will never turn into signed leases, but they're tracked the same way from the start.
Deal pipeline accuracy Every deal in the pipeline is a real, active deal. Reports and dashboards show only serious transactions. cleaner The pipeline will include many spaces that are just being evaluated — not yet real deals. Every report needs a permanent filter to exclude these, or the numbers look inflated.
What happens to spaces that don't move forward Rejected spaces stay in the evaluation list with a reason recorded — useful for understanding why spaces were passed on. Rejected spaces become closed-lost deal records. The history is preserved, but it adds volume to the deal database over time.
Broker experience Landlord Rep and Tenant Rep brokers work slightly differently — Tenant Rep has an extra "candidate list" step before deals are created. Both broker types work exactly the same way. One workflow to learn, one set of training materials.
AI agent readiness AI agents get a clean, unambiguous list of real deals to work with. No extra filtering or guesswork required. AI agents need to be told to ignore early-stage records when working with the deal pipeline — adds complexity to every agent built on top of this data.
Build complexity Slightly more to build upfront — one additional tracking list beyond what Landlord Rep requires. Simpler to build — same structure as Landlord Rep, just applied to Tenant Rep as well.
Recommendation Option A is recommended — the cleaner pipeline and AI-ready signals are worth the small upfront build cost. The extra candidate-tracking step reflects how Tenant Rep brokers actually work in practice.

Option B makes sense if simplicity and a single broker training experience take priority over pipeline accuracy.
Open Questions — Must Be Answered Before Build Begins
Can a single rep agreement cover multiple landlords?
This happens when a property has co-owners — e.g. two entities who jointly own a building and both need to sign. Question to answer: Is this a common scenario at M&M, or a rare edge case? The answer changes how the data model handles signatory tracking.
How should new inbound leads from MMI.com be handled?
Someone fills out a form on MMI.com — are they a brand-new contact, or someone already in the system under a different name or company? Question to answer: Will M&M license Salesforce Data Cloud to automatically detect and merge duplicates? Without it, deduplication is a manual process.
How should the total deal value roll up to the parent relationship?
A broker's overall relationship with a client (the parent deal) should reflect the combined value of all the individual transactions underneath it. Salesforce doesn't do this automatically. Question to answer: Who owns this requirement — technology team or business? The two available approaches have different build and maintenance costs.
What are the official stage names for each deal type?
Deal stages (e.g. "In Negotiation," "Agreement Signed") drive reports, dashboards, and broker quotas. Once real deals are in the system, stage names cannot be changed without corrupting historical data. Question to answer: Brokers need to review and sign off on the exact stage names before build begins — this is a business decision, not a technical one.
What do we call the sub-lease occupant?
When a tenant sub-leases their space to another party, that party needs a label in the system. "Sub-Tenant" is the most accurate term, but it may conflict with how M&M's brokers currently talk about these relationships. Question to answer: What term do brokers use today? That term should be used in the system to avoid confusion.
How many locations can a single tenant requirement cover?
A tenant might say "find me 10 locations across the country" — each location is tracked as a sub-requirement under the main one. There are practical limits on how deep this hierarchy can go before the system slows down. Question to answer: What is the realistic maximum number of locations a single Tenant Rep engagement covers? This needs to be tested before launch.
How should candidate space scores roll up to the overall requirement?
When a broker evaluates 20 spaces against a tenant's requirement, the system should show a summary score — "8 of 20 spaces are a strong fit." Salesforce doesn't calculate this automatically across related records. Question to answer: Who is responsible for building this calculation — and should it update in real time or on a schedule? The answer determines the approach and maintenance cost.

Salesforce Headless 360 · Agentic Architecture

Build the data model once.
Surface it everywhere brokers work.

The M&M leasing data model is not a CRM project. It is a data foundation — one source of truth for every Property, Space, Opportunity, and Lease. The question is not what lives in Salesforce. It is where brokers interact with it.

"Why should you ever log into Salesforce again?"

— Parker Harris, Co-Founder, Salesforce
The problem

Brokers will never use CRM.

Every CRM adoption study in commercial real estate reaches the same conclusion: brokers are revenue-generating principals, not data-entry clerks. Asking them to log into a UI to update deal stages, log calls, or mark spaces leased is a losing proposition — adoption stays at 20–30%, the data rots, and the platform fails.

→
The solution

Brokers never have to use CRM.

Salesforce Headless 360 decouples the data model from the interface. The rich object model M&M builds — Accounts, Properties, Spaces, Leases, Commission Splits — becomes a back-end API and AI context layer. Brokers interact with it through whatever surface they already live in: Microsoft Teams, Outlook, a voice call, a GPT-powered command interface, or a custom MMI.com broker portal.

Why This Is the Right Architecture for M&M
Principle 01
The data model is the asset, not the UI
The investment M&M makes in Account, Property, Space, Opportunity, and Lease relationships is durable. It survives UI changes, Salesforce releases, and AI tool generations. Headless architecture means the UI can be replaced — the data cannot be.
Principle 02
Agentforce requires rich data to be useful
AI agents are only as good as the data they read. A Requirement Matcher agent that queries a rich Requirement__c object with market, criteria, and status fields is categorically more useful than one reading flat spreadsheet rows. The data model built in Tab 1 is the prerequisite for everything in this tab.
Principle 03
Broker adoption follows the broker's context
Brokers live in email, phone calls, and deal conversations. The system that captures their work most completely is the one that meets them there — not the one with the best CRM UI. Ambient capture via voice, email, and chat surfaces is how M&M achieves real adoption.
Principle 04
Nothing writes without broker approval
Every ambient capture pattern — voice transcription, email context, AI suggestion — surfaces a broker approval card before writing to Salesforce. The broker is the authority, the AI is the assistant. This is the "JiLL pattern": AI drafts, broker approves, CRM stays clean.
Principle 05
M&M does not need a bespoke system to be differentiated
The differentiation is not in the code — it is in the data model, the broker workflows, the AI agents, and the integration decisions that encode M&M's leasing expertise. Salesforce provides the infrastructure; M&M's competitive advantage is what lives in it.
Principle 06
This pattern is already in production at enterprise scale
Leading commercial real estate firms have implemented this identical architecture — Salesforce data foundation, AI agent layer, and headless broker surfaces — with Broker Command Centers and Voice-to-CRM live in production. M&M is not the first mover; it is a fast follower with the advantage of learning from what has already shipped.

The CTO Decision

The question is not "should we build or buy a CRM." The question is: should we build and maintain a custom leasing application that replicates what Salesforce already does — object model, security, mobile, AI, integrations — while simultaneously hiring an engineering team to keep it current with AI capabilities that are evolving every six months? Or should we invest that same engineering capacity in the data model, the broker workflows, and the Agentforce agents that encode M&M's actual competitive knowledge — using Salesforce as the infrastructure those agents run on? The data model in Tab 1 is the moat. The headless architecture in this tab is how brokers access it without ever knowing it's Salesforce.
